# SAO Sky Map Processing Workflow for the CUDA Lunar-Orbit Imaging Pipeline

This README describes the standard sky-map preparation workflow used for the lunar-orbit radio visibility simulation and 3D reconstruction code.

The goal is to keep the data products physically consistent and easy to explain in the paper:

- the original Shanghai Astronomical Observatory (SAO) maps at `NSIDE=4096` are the canonical scientific inputs;
- all binary files store the **linear sky brightness map `B`** only;
- the CUDA forward visibility operator applies the pixel-area factor internally:

```text
pix_area = 4*pi/Npix
C[p] = B[p] * pix_area
```

Therefore, the Python preprocessing scripts must **not** premultiply `B` by pixel area.

---

## 1. Canonical data convention

For the current manuscript, the canonical SAO maps are treated as:

| Item | Convention |
|---|---|
| Source | SAO simulated full-sky maps |
| Native resolution | `NSIDE=4096` |
| HEALPix order | `RING` |
| Coordinate system | Ecliptic |
| HDF5 dataset | `skymap` |
| Binary format | raw little-endian `float32`, no header |
| Binary content | linear sky brightness `B`, not `log10(B)`, not `B*pix_area` |
| CUDA option | `--sky_order=ring --apply_pixel_area=1` |

The `NSIDE=512` maps are generated by degrading the native `NSIDE=4096` maps and are used for small-scale validation and debugging.

The `NSIDE=16384` maps are generated by nearest-parent upsampling and are used only as controlled scalability stress-test workloads. They do not introduce new physical small-scale sky structures.

---

## 2. Why the pixel-area factor is not saved in the bin file

The original MATLAB visibility simulation uses:

```matlab
s = 4*pi/npix;
C = single(B.*s);
...
Viss = sum(C .* H .* exp(...));
```

This is a pixel-area-weighted approximation to the sky integral:

```text
V(u,v,w) = sum_p B[p] * DeltaOmega[p] * H[p] * exp(-2*pi*i*phase[p])
```

where:

```text
DeltaOmega[p] = 4*pi/Npix
```

To keep all resolutions consistent, the bin files store only `B`. The CUDA code should apply `4*pi/Npix` at runtime. This makes the following operations consistent:

- `4096 -> 512`: average brightness values when degrading;
- `4096 -> 16384`: copy parent brightness values when upsampling;
- `1 MHz / 10 MHz / derived 30 MHz`: all maps keep the same brightness-map meaning.

---

## 3. Deriving a 30 MHz map from available 1--10 MHz maps

If a native SAO 30 MHz map is unavailable, we derive a controlled 30 MHz workload from the available SAO `1--10 MHz` maps at `NSIDE=4096`.

For each pixel, the script fits a log-frequency model:

```text
log B(nu) = a0 + a1 log(nu)
```

by default. The derived 30 MHz map is then:

```text
B_30 = exp(a0 + a1 log(30 MHz))
```

This is an **effective spectral-index extrapolation** from the available same-coordinate, same-order SAO maps. It is better than assigning a random spectral index, but it is still a derived frequency-scaled product, not an independent SAO 30 MHz simulation.

The script also supports a degree-2 log-polynomial fit:

```text
log B(nu) = a0 + a1 log(nu) + a2 log(nu)^2
```

However, degree 2 can be less stable for extrapolation from 10 MHz to 30 MHz. Use it only as a sensitivity test unless validated.

Recommended paper wording:

```text
The 30 MHz map is derived from the SAO 1--10 MHz NSIDE=4096 maps by a per-pixel log-frequency fit. It is used as a controlled high-frequency workload rather than an independent astronomical simulation product.
```

## 4. Output directory structure

A typical output root looks like this:

```text
sky_sao_processed/
  1M_n4096_ring_ecliptic/
    B_1M.bin
    B_1M.bin.json

  10M_n4096_ring_ecliptic/
    B_10M.bin
    B_10M.bin.json

  30M_n4096_derived_from_1M_to_10M_ring_ecliptic/
    B_30M.bin
    B_30M.bin.json
    effective_beta_1M_10M_to_30M.bin        # optional
    fit_log_rmse_1M_10M_to_30M.bin          # optional
    fit_products.json                       # optional

  30M_n512_from4096_ring_ecliptic/
    B_30M.bin
    B_30M.bin.json

  30M_n16384_from4096_ring_ecliptic_stress/
    B_30M.bin
    B_30M.bin.json
```

Each `.json` file records the source, resolution, order, coordinate system, generation method, and intended usage.

## 5. Example commands

### 5.1 Export native 1--10 MHz maps and derive a 30 MHz map

Edit the paths below to match your actual HDF5 file names.

```bash
python make_sao_sky_products.py \
  --inputs \
    1:/path/to/1.0MHz_with_absorption.hdf5 \
    2:/path/to/2.0MHz_with_absorption.hdf5 \
    3:/path/to/3.0MHz_with_absorption.hdf5 \
    4:/path/to/4.0MHz_with_absorption.hdf5 \
    5:/path/to/5.0MHz_with_absorption.hdf5 \
    6:/path/to/6.0MHz_with_absorption.hdf5 \
    7:/path/to/7.0MHz_with_absorption.hdf5 \
    8:/path/to/8.0MHz_with_absorption.hdf5 \
    9:/path/to/9.0MHz_with_absorption.hdf5 \
    10:/path/to/10.0MHz_with_absorption.hdf5 \
  --dataset skymap \
  --out-root sky_sao_processed \
  --coordinate ecliptic \
  --make-native-bins \
  --derive-target-freq 30 \
  --derive-degree 1 \
  --save-fit-maps
```

This produces native `B_1M.bin` through `B_10M.bin` and a derived `B_30M.bin` at `NSIDE=4096`.

### 5.2 Derive 30 MHz and create 512 / 16384 products

```bash
python make_sao_sky_products.py \
  --inputs \
    1:/path/to/1.0MHz_with_absorption.hdf5 \
    2:/path/to/2.0MHz_with_absorption.hdf5 \
    3:/path/to/3.0MHz_with_absorption.hdf5 \
    4:/path/to/4.0MHz_with_absorption.hdf5 \
    5:/path/to/5.0MHz_with_absorption.hdf5 \
    6:/path/to/6.0MHz_with_absorption.hdf5 \
    7:/path/to/7.0MHz_with_absorption.hdf5 \
    8:/path/to/8.0MHz_with_absorption.hdf5 \
    9:/path/to/9.0MHz_with_absorption.hdf5 \
    10:/path/to/10.0MHz_with_absorption.hdf5 \
  --dataset skymap \
  --out-root sky_sao_processed \
  --coordinate ecliptic \
  --derive-target-freq 30 \
  --derive-degree 1 \
  --save-fit-maps \
  --make-nside512 \
  --make-nside16384 \
  --resample-freqs 30 \
  --integral-check
```

This creates:

- `30M_n4096_derived.../B_30M.bin`
- `30M_n512_from4096.../B_30M.bin`
- `30M_n16384_from4096..._stress/B_30M.bin`

### 5.3 Create only a 10 MHz 16384 resolution-scaling stress map

```bash
python make_sao_sky_products.py \
  --inputs 10:/path/to/10.0MHz_with_absorption.hdf5 \
  --dataset skymap \
  --out-root sky_sao_processed \
  --coordinate ecliptic \
  --make-native-bins \
  --skip-derived \
  --make-nside16384 \
  --resample-freqs 10 \
  --integral-check
```

Use this only for same-frequency resolution-scaling stress tests.

## 7. Sanity checks

### 7.1 File sizes

Expected raw float32 sizes:

| NSIDE | Npix | Size |
|---:|---:|---:|
| 512 | 3,145,728 | about 12 MiB |
| 4096 | 201,326,592 | about 768 MiB |
| 16384 | 3,221,225,472 | about 12.0 GiB |

### 7.2 Pixel-area-weighted sky integral

For a brightness map `B`, compute:

```python
import numpy as np
import healpy as hp

B = np.fromfile('B_10M.bin', dtype=np.float32).astype(np.float64)
nside = 4096
pix_area = 4*np.pi / hp.nside2npix(nside)
print(np.sum(B * pix_area))
```

The integral should remain close across:

- native `NSIDE=4096`;
- degraded `NSIDE=512`;
- nearest-parent upsampled `NSIDE=16384`.

Small differences are expected due to `float32` storage and resampling.

### 7.3 Visualization

The products are in RING order:

```python
import numpy as np
import healpy as hp
import matplotlib.pyplot as plt

B = np.fromfile('B_30M.bin', dtype=np.float32)
hp.mollview(np.log10(np.maximum(B, 1e-30)), nest=False, title='RING sky map')
plt.show()
```

Use `nest=False`. Do not confuse RING/NEST ordering with Galactic/Ecliptic/Equatorial coordinates.

These maps are represented with HEALPix \(N_{\mathrm{side}}=4096\) in RING ordering and in the ecliptic coordinate system. ---

## 9. Important limitations

1. The derived 30 MHz map is not an independent SAO 30 MHz simulation.
2. The `NSIDE=16384` maps are stress-test inputs, not true high-resolution scientific sky simulations.
3. Degree-1 fitting gives an effective spectral index. It is robust and easy to explain, but it may not fully capture absorption curvature.
4. Degree-2 fitting can capture curvature but may extrapolate unstably. Treat it as a sensitivity test.
5. All CUDA runs should use the sky order consistent with the bin file: `--sky_order=ring` for the products generated here.
